## 0. 先做通用底座

这四件事要在任何一个机器之前做完，后面 8 个方块全都踩在它们上面。

### 0.1 知识系统 —— 一个接口，所有解锁都走它

**[已确认]** 配方要能靠"观察过某种微生物"来解锁；每种微生物都要有一个现成的接口，
以后解锁日志、解锁配方、解锁成就都复用同一条路。

- 每个玩家一份 `Knowledge`：用 NeoForge 的 data attachment 存，`copyOnDeath()` 保命，
  `sync(...)` 同步到客户端（UI 要显示"未知"，客户端必须知道）。
- 节点 id 约定：

| 前缀 | 含义 | 例子 |
|---|---|---|
| `beyondtime:microbe/<微生物id>` | 在显微镜里见过这种微生物 | `beyondtime:microbe/ancient_water` |
| `beyondtime:tissue/<生物id>` | 分析过这种生物的组织 | `beyondtime:tissue/enderman` |
| `beyondtime:machine/<机器id>` | 解锁了某台机器 / 某种配方 | `beyondtime:machine/centrifuge` |

  **每种微生物自动获得一个节点**（由微生物自己的 id 推出来），以后加新微生物不用碰知识代码。
- 两个入口，缺一不可：
  - `observe(player, node)` —— 玩家自己看到了（显微镜里第一次见到某微生物时调用）。
  - `grant(player, node)` —— 剧情 / 成就直接授予。**伪古水菌必须走这条**，因为它在镜下
    和古水菌长得一样，玩家永远"观察"不出来。
- 触发时机：**[待确认]** 建议放在"显微镜里第一次看到"，而不是采集的时候 ——
  这样"采到"和"知道"是两件事。
- 消费者：日志书、配方书、成就/提示、机器 UI。
- 配方解锁走原版现成的 API：`ServerRecipeBook#addRecipes`（`net/minecraft/stats/ServerRecipeBook.java:61`），
  它一次做完"标记已解锁 + 高亮 + 发通知包 + 触发 `RECIPE_UNLOCKED`"，不用写自定义成就触发器。

> **已知限制（作者知悉即可，不必处理）**：原版工作台只能做到"配方书里看不见"。
> 26.2 没有可取消的合成事件，玩家如果记得摆法仍能手动摆出来。真要硬拦，只能把配方搬进机器。

### 0.2 组织样本数据组件

一个 `beyondtime:tissue` 组件，记录：`entity`（哪种生物）+ `analysis`（分析程度）+ 来源。

| 分析程度 | 怎么来的 | 能看到什么 |
|---|---|---|
| `NONE` | 刚采下来 | 什么都没有 |
| `PARTIAL` | 基础生物分析仪 | 残缺的、看一次就没的信息 |
| `FULL` | 高级生物分析仪 | 完整信息，且被机器存档 |

采样器、两台分析仪、编辑仪、培养器、克隆舱全都读同一个对象，不为每个机器发明一种样本物品。

### 0.3 机器基类与 UI 框架

8 个方块里有 5 个是"输入 → 耗时 → 输出"。抽一个公共基类，只写配方类型和界面，
界面沿用显微镜那套（左边载物台/图谱，右边文字报告）。**8 套独立 UI 是这次最大的工期风险。**

### 0.4 数值全部数据驱动

配方、解锁条件、燃烧值都放 `data/beyondtime/...`，以后加内容不改代码。
（仙灵浓度不单独建表，直接复用 0.5 说的方块微生物信息。）
配方的解锁条件写成一条一条的数据，例如：

```json
{ "recipe": "beyondtime:centrifuge",
  "requires": { "any": [ "beyondtime:microbe/copper", "beyondtime:microbe/stone" ] } }
```

### 0.5 仙灵浓度 = 方块微生物信息里的仙灵量

**[已确认]** 能量供应器**不单独建一张"仙灵浓度表"**，而是**直接读 `MicrobeProfiles`
里每个方块的仙灵（`fae`）权重**当浓度用。

好处：方块信息里本来就已经写着"附魔台 仙灵 30"、"紫水晶块 仙灵 22"这种，
能量规则和世界观自然一致 —— 玩家可以靠显微镜自己推出"哪块砖发电多"，
不需要再多记一套数字。

- 实现：给 `MicrobeProfiles` 加一个查询（例如 `aura(BlockState)`），
  返回该方块混合里的仙灵权重，查不到就是 0。标签条目（如 `#logs`）同样参与。
- **[已确认] 后期再加**：现在只有已有条目的方块有仙灵值，以后给更多方块补条目就行，
  能量那边一行都不用改。
- **[待确认]** 供能范围（建议 9×9×5）、底值、上限、点数→FE 的换算系数。

## 4. 建议的开发顺序

理由：2/3 能立刻验证知识系统好不好用；4 提前做，5~8 才不会全部返工；6/7/8 是长链，放最后。

1. 知识系统（底座）
2. 采集器 + 密封组织样本（第一个"拿到数据"的入口）
3. 基础生物分析仪（第一次"消费数据"）
4. 能量供应器（后面三个都要用电）
5. 高级生物分析仪（档案 + 与日志/谱图联动）
6. 生物组织培养器 + 营养素制造机（互相依赖的一对）
7. 生物编辑仪
8. 克隆舱（收尾）

## 7. 实现计划（先不动代码，先把结构定下来）

### 7.1 名单做成实体标签，不写死在代码里

可采集 / 可克隆的名单做成**实体类型标签**：

```
data/beyondtime/tags/entity_type/samplable.json   ->   #beyondtime:samplable
```

代码里只有一句 `entity.getType().is(BTEntityTags.SAMPLABLE)`。好处：
改名单 = 改一个 JSON；以后想加"只在新维度里出现的生物"也不用重新编译；
玩家/整合包还能用数据包自己增删。

### 7.5 分步计划与"完成标志"

每一步做完都会提交并推送，作者双击 `tools\dev-client.bat` 就能看效果。

| 步 | 做什么 | 完成标志（作者能在游戏里验的） |
|---|---|---|
| 1 | 知识系统 + attachment + 名单标签 + `tissue` 数据组件 | 打底，暂时看不到变化 |
| 2 | 采集器 + 密封组织样本 | 打名单里的生物掉样本、打别的生物不掉；3 个样本后采集器爆掉 |
| 3 | 基础生物分析仪 | 放样本进去能看**一次**残缺报告，关掉就回不去 |
| 4 | 能量供应器（FE） | 机器放在旁边能充上电；周围仙灵方块越多充得越快 |
| 5 | 高级生物分析仪 | 耗电分析，档案能切换回看，不覆盖 |
| 6 | 培养器 + 营养素制造机 | 能造营养素、能培养组织、能自动抽正下方的水 |
| 7 | 生物编辑仪 | 能合成"不存在的样本"（配方等作者给） |
| 8 | 克隆舱 | 能克隆出 1 滴血、1 分钟新生的生物 |

### 7.6 刻意**不**新建的东西（避免重复造轮子）

- **不新建仙灵浓度表**：直接用方块微生物信息里的仙灵权重（0.5）。
- **不新建第二套配方系统**：能塞进原版 `Recipe` 的就塞；只有"培养 / 合成营养素"这种
  多输入带时间的才写自定义配方类型。
- **不新建两套存储**：日志进度 = 每个玩家的 attachment；机器档案 = 方块实体自己存盘。
  两者各管各的，正好对应"日志每人独立、机器大家共享"这条规则。
- **不新建能量单位**：用 FE，机器统一挂 `Capabilities.Energy.BLOCK`。
- **不动已有的显微镜 / 培养皿代码**，新东西都是叠加。
