# Beyond-Time 设计文档

> 本文只写**已确定的规则、协作流程与技术框架**。
> 世界观、故事、微生物、过去生物、维度等设定**全部由作者（项目所有者）提供**，
> 开发方不自行设计；需要时按 `docs/LORE_INTAKE.md` 的登记表逐项确认后再实现。

目标平台：Minecraft 26.2 / NeoForge 26.2.0.88 / Java 25
模组名：**Beyond-Time**（暂定）· mod id：`beyondtime` · 包名：`com.beyondtime`

---

## 1. 模组定位（作者给出的需求原文）

> 制作一个探索 MC 历史的模组，从制作显微镜观察微生物到观察各种生物的组成，
> 逐渐发现一些古老的故事，到克隆出部分生物过去的形态，研究末影人、村民（刌民）、
> 监守者、远古守卫者的古老版本的克隆体，最后发现失落的魔法和科技，
> 制造出能回到各个维度过去的机器，去发现为什么末影人怕水、为什么猪灵和疣猪到主世界
> 就会僵尸化、为什么地狱和末地显然以前都有很多水，但最后末地变成虚空、地狱变成高温
> 等等的很多秘密。

## 2. 已确定的硬规则

这些是作者定下的边界，开发时不得违反：

| # | 规则 | 对开发的影响 |
|---|---|---|
| R1 | 过去维度的**数量现在不固定**，先预留 **7 个**槽位，用不完的做成彩蛋维度或废弃 | 代码与数据里按 7 个可扩展位预留，不写死数量 |
| R2 | 维度的具体设计**排在大部分衍生方块与物品设计完成之后** | 里程碑顺序：物品/方块/机器 → 微生物 → 克隆 → 维度 |
| R3 | 微生物**不做实体**，也**不在非显微 UI 中渲染** | 微生物 = 数据 + 显微界面内的图形表现；世界里不出现菌落实体/贴图 |
| R4 | 微生物**种类不多、不繁殖、不利用**；作用只有两个：判定环境、发现与剧情相关的微生物并逐步推进 | 不做培养扩增/资源化玩法；培养皿等只作为"发现/鉴定"环节（具体机制待定） |
| R5 | 穿越回到过去**不影响现在**（中间隔了极长时间） | 过去维度与现行世界完全隔离，不改动主世界存档，不做"改变历史"的因果逻辑 |
| R6 | 时空机器**不能随意回溯**：必须先有该时代的**生物参照**，并收集到**关键物品**，才能开启指定时代 | 时代解锁 = 前置生物复活 + 关键物品收集，做成明确的解锁条件 |
| R7 | 贴图统一 **32×32** | 所有物品/方块贴图按 32×32 制作与校验 |
| R8 | 故事背景、设定、微生物、过去生物、维度**由作者定义** | 开发方只做实现；不清楚的先提问，不自行补设定 |
| R9 | 测试由作者进行 | 开发方负责构建通过与提供便捷的调试渠道，不代替试玩 |

## 3. 协作方式（重要）

```
作者写设定 / 提需求  →  开发方确认理解(提问)  →  实现  →  作者试玩测试  →  反馈迭代
```

- **设定来源**：所有世界观内容写在 `docs/LORE_INTAKE.md`（登记表）里，或由作者直接口述，开发方录入。
- **提问机制**：任何设定空白（名字、外形、行为、数值、剧情顺序）都不猜，先提问；提问要具体到可勾选。
- **一次一小步**：每个功能独立提交，提交信息写清"实现了什么、还缺什么设定"。
- **不自由发挥**：开发方不得自行添加设定类的物品/生物/结构；纯技术性的辅助（如调试命令、数据生成）除外。
- **编号引用**：登记表里的条目带编号（如 `M-03`、`B-02`、`E-1`），代码与提交信息引用编号，便于对照。

## 4. 技术框架

### 4.1 包结构

```
com.beyondtime
  BeyondTime            入口（模组总线 + 游戏总线）
  BeyondTimeClient      客户端入口（渲染器/界面/粒子注册）
  registry/             BTRegistries 及各内容注册表
  item/ block/ entity/ blockentity/ menu/ network/
  microbe/              微生物数据、显微观察逻辑
  research/             进度、解锁、图鉴数据
  worldgen/             维度、生物群系、结构、特征（最后阶段）
  datagen/              数据生成提供器
  client/               渲染器、界面、模型
  command/              调试命令
  compat/               可选联动
```

### 4.2 关键实现策略

| 主题 | 方案 |
|---|---|
| 注册 | 统一走 `BTRegistries` |
| 数据生成 | 方块/物品/语言/战利品/配方/标签，以及后续维度的 `dimension_type`/`dimension`/`noise_settings`/`biome`/`structure` JSON，全部 datagen 产出并提交 |
| 微生物 | 用数据组件 + 数据驱动定义描述；**只在显微界面里绘制**，无实体、无世界贴图 |
| 显微观察 | 服务端权威判定（观察到什么由服务端算），客户端负责表现 |
| 解锁与进度 | 玩家进度用 NeoForge 数据附件，世界级进度用 `SavedData`；7 个时代槽位做成可扩展的枚举/数据驱动列表 |
| 网络 | 自定义 payload，同步观察结果、解锁状态、机器进度 |
| 渲染 | 自定义方块模型走 JSON/Blockbench；实体模型走 Java 模型 |
| 非完整方块 | 模型（手写 JSON）与碰撞箱（`getShape`）是**成对**的两处数字，必须一起改；细节与坐标表见 `docs/MICROSCOPE.md` |
| 兼容 | 不硬依赖第三方模组 |

### 4.3 26.2 版本注意点

- 官方名称空间、无混淆：`net.minecraft.resources.Identifier`（不是 `ResourceLocation`）。
- Java 25 工具链；MC 26.2 与 NeoForge 版本必须匹配。
- API 细节以官方 26.2 源码/文档为准，逐条核对后再写。

## 5. 素材规格（作者制作）

| 类型 | 规格 | 路径 |
|---|---|---|
| 物品贴图 | **32×32** PNG，可带透明 | `assets/beyondtime/textures/item/<name>.png` |
| 方块贴图 | **32×32** PNG | `assets/beyondtime/textures/block/<name>.png` |
| 方块模型 | JSON，**手写**，放 `src/main/resources`（datagen 只生成 blockstate，不生成模型） | `assets/beyondtime/models/block/<name>.json` |
| 实体模型 | Blockbench → Java 实体模型 JSON + 贴图 | 贴图 UV 与模型一致 |
| 容器界面背景 | **256×256** PNG，可见面板画在左上角 176×166 内 | `assets/beyondtime/textures/gui/<name>.png` |
| 音效 | OGG（可选） | `assets/beyondtime/sounds/` |

说明：

- `.bbmodel` 会被构建排除，不会进 jar。
- 模型里不写 `uv` 时，**一个面 = 整张贴图铺满一次**（贴图按 0..16 的坐标空间使用，
  所以 32×32 相当于更高分辨率，不会变形）。想在一张图上切多块分别取用，才需要写
  `"uv": [...]`。
- 容器界面背景必须是 **256×256**（原版所有容器界面都是这个尺寸）。给成别的尺寸会被拉伸，
  槽位、文字全部错位 —— 这就是显微镜界面一开始错位的原因。
- 更细的贴图规格、固定坐标表在 `docs/MICROSCOPE.md` 第 4 节。

## 7. 已确认的决定与待确认项

### 7.1 已确认（作者已回答，已并入实现）

1. 显微镜合成里的"紫水晶"= **紫水晶碎片** (`minecraft:amethyst_shard`)，不是紫水晶块。
2. 清洗 = **装水的炼药锅**，正下方必须是**篝火 / 灵魂篝火 / 岩浆块 / 熔岩**之一
   （装熔岩的炼药锅不算；炼药锅下方是熔岩才算热源）。清洗一次消耗一格水。
3. **不需要** `/beyondtime` 调试命令。测试用创造模式页签/配方书即可。
4. 7 个时代槽位**先占位命名** `era_1` … `era_7`，名字以后再定（落地时间在 M6 之前）。
5. **破坏带培养皿的显微镜**：显微镜本体**不带**培养皿掉落，培养皿**单独掉在地上**
   （按此设计，不再改成"保留在显微镜里"）。
6. 显微镜**不是完整方块**：台面仪器造型、四个朝向、碰撞箱 = 外形。
   外形方案、切换方法与贴图规格见 `docs/MICROSCOPE.md`。
7. **培养皿采集样本后不可堆叠**（`1`）；干净的培养皿仍然堆叠 `64`。
8. 显微镜/培养皿的**贴图由作者制作**，规格见 `docs/MICROSCOPE.md` 第 4 节。

### 7.2 还在等回答

1. 清洗**消耗一格水**要保留吗？（参照原版水瓶取水；不想要就说一声，改成不消耗。）
2. 培养皿**对着任何方块右键都会采集**（因为方块先于物品处理右键）：目前拿培养皿右键箱子、熔炉、

   或"只对特定方块采集"吗？

### 7.3 实现细节备忘（可能与直觉不同）

1. **显微镜掉落流程**：`BlockEntity.preRemoveSideEffects` 会先把培养皿掉到地上，
   之后战利品表执行时方块实体已经不在了，所以掉出来的显微镜是**空的**。
   战利品表里那段 `copy_components(beyondtime:contained_dish)` 因此目前是死代码，
   留作"将来改成保留培养皿"的接口。
2. **显微镜最多放 1 个培养皿**：培养皿本身可堆叠（干净时 64），但槽位上限是 1。
3. **显微镜右键行为**：手上拿着培养皿且显微镜是空的 → 直接放入；其它情况（空手、手上有别的东西、
   里面已经有培养皿）→ 打开界面。界面里也能正常放入/取出。
4. **界面背景必须 256×256**，可见面板画在左上角 176×166 里；槽位坐标是定死的，
   见 `docs/MICROSCOPE.md` 第 4.4 节。
